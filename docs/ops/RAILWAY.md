## מקור התצורה

ההגדרות הפעילות נשמרות בשירותים ב־Railway. החל מ־5.10 hamenoa מחובר למאגר `avf204-del/forceapp`, ענף `codex/release-2026-10-05`, עם פריסה אוטומטית פעילה לענף זה. דחיפה ל־main בלבד אינה פריסה. החל מפריסת N14 ב־6.10 שירות hamenoa-backup מחובר גם הוא למאגר GitHub, ללא trigger אוטומטי; הוא נפרס במפורש עם commit מלא באמצעות `serviceInstanceDeployV2` לאחר שהמיגרציות הושלמו; אין לשנות את ה־cron או הווליום אגב עדכון האפליקציה.

ב־Codex Cloud אומתה קריאת GraphQL עם `RAILWAY_TOKEN`, אך העלאת ארכיון דרך `railway up` נדחתה במנגנון הסודות של הפרוקסי. אין לנסות לעקוף אותו או להדפיס את הטוקן. אחרי שהבעלים חיבר את המקור בממשק Railway, ניתן לעקוב אחר הפריסה מהענף המחובר; הסכמה הרשמית מאפשרת גם `serviceInstanceDeployV2` עם `environmentId`, `serviceId` ו־`commitSha` מלא מהמאגר המחובר. לפני התחלת פריסה נוספת בודקים אם אותה גרסה כבר נבנית, כדי למנוע כפילות. החלפת מקור וחיבור מאגר מחייבים הרשאת חשבון שאינה זמינה בהכרח לטוקן פרויקט.

ב־20.9 אומת שהשירות התעלם מפקודות קובץ `railway.json`, אף שמטא־דאטה של הפריסה הזכיר את הנתיבים בקובץ. ניסיון לקבוע קובץ תצורה ייעודי לגיבוי נדחה ב־API עקב ביטול התמיכה בהגדרת Config as Code חדשה. הקבצים הוסרו כדי למנוע תחושת ביטחון שגויה. הגדרות השרת נקבעו ישירות ב־API של השירות; אינן משתני סביבה ואינן סודות.

## פקודת העלאה

להריץ משורש `app`, לאחר שמירת השינויים בגיט ובדיקת קיום גיבוי מתאים. `.env.deploy` נשאר מקומי; אין להדפיסו או להכניסו לארכיון הפריסה. ה־CLI מכבד `.gitignore` ו־`.railwayignore`.

```bash
DOTENV_CONFIG_PATH=.env.deploy node --import dotenv/config -e '
  const { spawnSync } = require("node:child_process");
  const result = spawnSync("pnpm", [
    "dlx", "@railway/cli@5.57.11", "up",
    "--project", "7dd26f03-17f7-45c7-9dc2-63c6dfc9beb8",
    "--environment", "production", "--service", "hamenoa", "--detach", "--json"
  ], { stdio: "inherit", env: process.env });
  process.exit(result.status ?? 1);
'
```

פריסת הגיבוי הנוכחית משתמשת במקור GitHub וב־`serviceInstanceDeployV2` עם commit מלא, רק אחרי שהמיגרציה שהקוד תלוי בה הסתיימה. פקודת CLI ההיסטורית אינה נדרשת למסלול זה. לשמר את לוח הזמנים ואת ה־volume; אין להעלות את תיקיית `backups` המקומית. שינוי בפקודות השירות מתבצע בהגדרות השירות, לא באמצעות החזרת `railway.json`.

## אימות ושחזור שירות

1. לפני העלאה: `git status`, בדיקות רלוונטיות, זיהוי commit, בדיקת הגדרות שני השירותים ורישום הגיבוי הזמין וגילו.
2. אחרי העלאה: לשמור deployment ID; לבדוק `deployment list` עד `SUCCESS` וגם את לוגי ההכנה/העלייה. `--detach` אינו ממתין, וגם סיום build אינו מספיק.
3. לאמת במסד בקריאה בלבד שהמיגרציה רשומה עם `finished_at` ושדותיה/האינדקסים שלה קיימים. אין צורך לייצא נתוני משתמשים לבדיקה זו.
4. לבדוק `/`, `/login`, `/privacy`, `/terms`, ואת הגנת נתיבי API ללא הזדהות. בדיקות אלה אינן תחליף למסלול אימון מחובר; אין ליצור אימוני בדיקה לחשבון אמיתי.
5. לשירות הגיבוי: לוודא שהגרסה החדשה משתמשת בפקודת הגיבוי, מסיימת בהצלחה, רושמת את כל הטבלאות ושומרת ליעד הענן הקיים. לאמת מצב לפי מקור בחיווי הניהול.
6. בכשל אפליקטיבי: אפשר לחזור לפריסת השרת הקודמת. המיגרציה של 20.9 מוסיפה שדות ואינדקסים ותואמת לקוד הקודם; אין למחוק אותם או לשחזר מסד באופן אוטומטי. שחזור נתונים הוא פעולה נפרדת לפי [מדריך האחסון](STORAGE.md).
